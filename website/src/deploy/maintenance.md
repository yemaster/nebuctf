# 备份、升级与恢复

平台备份需要同时保存数据库、文件和配置。仅导出题目或比赛，不能恢复账号、报名、提交和历史成绩。

## 需要保留什么

| 内容 | 用途 |
| --- | --- |
| PostgreSQL 逻辑备份 | 账号、题目、比赛、任务与成绩 |
| 文件卷 | 附件、报告、海报、头像等上传资料 |
| `.env` 或部署 Secret | 站点密钥、数据库连接及运行策略 |
| 题目镜像与部署版本 | 恢复环境和核对版本 |
| 流量文件 | 需要保留的统计与抓包记录 |

站点密钥必须与备份一起保留，但应与公开代码、导出包分开存放。

## 备份与恢复验证

Compose 部署可以在仓库根目录备份数据库：

```sh
mkdir -p backups
chmod 700 backups
umask 077
docker compose exec -T db pg_dump -U nebuctf -d nebuctf -Fc > backups/nebuctf.dump
```

使用维护窗口协调数据库和文件备份，避免上传、比赛提交或后台任务继续修改其中一方。文件卷要保留权限和所有者。备份结束后，在独立空数据库与独立文件目录恢复并检查，不能只看备份命令是否返回成功。

验证至少包括用户和比赛数量、静态附件下载、历史成绩、站点密钥可用性以及一题完整的靶机链路。不要在正式库上试跑恢复命令。

## 升级顺序

1. 阅读本次变更，记录当前提交、镜像和配置。
2. 完成数据库与文件备份，在隔离环境验证迁移。
3. 安排维护窗口，处理活动靶机和正在执行的判题任务。
4. 更新平台版本，先让 API 完成迁移，再更新 Scheduler、Runtime 和 Web。
5. 检查服务状态、健康接口、资源心跳和关键业务流程。

代码回滚不等于数据库回滚。新字段或执行规则已经投入使用时，旧 Runtime 可能无法遵守新规则，应先判断兼容性，再决定回滚代码还是恢复整份备份。

## 日常检查

关注磁盘空间、数据库备份、Runtime 心跳、排队任务、失败资源和镜像占用。长期不用的环境应通过平台释放，确认清理完成后再停 Runtime。

实例历史用于计算比赛累计开启次数，不应作为普通日志直接删除。禁止用 `docker compose down -v` 作为日常停止方式，它会删除声明的持久卷。
