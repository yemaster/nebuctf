# API 与个人密钥

业务接口统一使用 `/api` 前缀。网页通过同源会话访问；自动化脚本可在管理员开放后使用个人 API KEY。

## 创建密钥

管理员先在 API KEY 策略中开启功能，配置允许的权限、有效期和可选身份。用户在账号设置中创建密钥，可以选择身份，也可以手动选择允许的范围。

完整密钥仅在创建成功时显示一次。保存到本地密钥管理工具或 CI Secret，不要提交到仓库。停止使用后从账号设置撤销。

密钥的实际权限取决于管理员当前允许范围、创建时保存的权限和账号本身的访问权。比赛报名、组别权限、资源归属及限流仍会检查。

## 调用接口

将平台地址和密钥放入本地环境变量后调用，下面示例不包含真实凭据：

```sh
curl --fail-with-body \
  -H "Authorization: Bearer $NEBUCTF_API_KEY" \
  "$NEBUCTF_ORIGIN/api/challenges"
```

应为这次请求授予题目读取范围，并在正式环境使用 HTTPS。不要将完整密钥粘贴到 URL、截图或错误报告里。

## 查看可用接口

平台提供按当前允许范围过滤的 API 文档。公开目录 `/api/api-keys/catalog` 返回当前开放的范围和身份，准确的方法、路径和作用以平台文档为准。

密钥不能管理自身生命周期、修改密钥策略、密码和安全权限，也不用于 WebSocket。需要这些操作时使用网页登录会话。

## 处理失败

| 状态 | 常见原因 |
| --- | --- |
| 401 | 密钥无效、过期、撤销，或账户被停用 |
| 403 | 功能未开启、权限范围不足，或业务访问被拒绝 |
| 409 | 当前状态冲突、配额或次数已达上限 |
| 429 | 操作过于频繁，按返回的等待时间重试 |

带有 Authorization 的请求不会在密钥失败后退回 Cookie 或匿名身份。写权限也不隐含读权限，需要读取结果时一并选择相应范围。
