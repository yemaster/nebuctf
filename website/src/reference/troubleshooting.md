# 故障排查

先确定问题发生在网页、API、Runtime 还是题目服务。记录时间、题目和实例 ID，以及不包含凭据的错误信息，再查看对应日志。

## 平台无法访问

检查 Web 和 API 是否运行、外层代理是否转发到正确端口，以及域名是否解析到当前主机：

```sh
docker compose ps
docker compose logs --tail=100 web api
curl --fail http://localhost:8080/api/health
```

健康接口返回成功后，再检查浏览器请求是否被 HTTPS、代理或错误的域名阻断。

## 登录或保存提示来源不符

核对浏览器地址与 `APP_ORIGIN`，包括协议、域名和端口。HTTPS 配置 `COOKIE_SECURE=true`，本地 HTTP 则为 false。修改配置后重建对应服务，不要关闭 Origin 或 CSRF 检查。

## 环境一直排队

检查 Runtime 是否在线、数据库是否一致、资源池是否已满，以及旧环境是否还在回收：

```sh
docker compose logs --tail=100 worker
docker compose logs --tail=100 scheduler
```

多容器题按全部服务累计 CPU、内存与容器数，不能只看主服务配置。比赛的每队或全场名额也可能阻止创建。

## 镜像存在，但启动失败

确认镜像在 Docker Runtime 主机中，而不是只存在于开发机器或 k3s 的 containerd。检查镜像架构、允许前缀、非 root 权限、只读目录和健康检查。

服务应监听 `0.0.0.0`，与题目端口一致。先让镜像在合理资源配额下通过测试，再调整正式比赛的配置。

## 专属附件生成或下载失败

确认生成器无网络也能完成任务，镜像含 `/bin/tar`，产物为 `/output/artifact.zip`，不超过 20 MiB，并在生成后保持进程存活。

如果生成成功而下载失败，检查 API 与 Runtime 的数据卷是否一致，以及文件用户、组和权限是否匹配。

## 能访问平台，不能访问题目

端口题检查 `CHALLENGE_HOST`、端口范围、云防火墙和宿主防火墙；域名题检查通配符 DNS、证书、Host 转发及 gateway。WebSocket 失败时检查外层代理的升级头和超时。

## 次数用完后如何处理？

冷却结束只允许再次操作，不会恢复累计开启次数。管理员需要根据赛事规则调整统一或单题上限。不要通过删除实例历史重置次数。

## 报告问题时附带什么？

提供平台版本、部署方式、复现步骤、预期结果和实际结果。日志应移除密码、密钥、Cookie、邀请码和 Flag；错误截图也应检查是否包含选手私人资料。
